The audit shifted the objective from generating the quotation to controlling the lifecycle that prepares it.

The pivot is from "generate the quotation" to "control the lifecycle that prepares it." Left = original client request (AI-generated BOQ as autonomous estimation target). Center = the audit's decision: rejected as autonomous, for two reasons — (1) Tacit expertise: the BOQ / Estimation Workbook is the output of expert reasoning (material behavior, fabrication complexity, supplier reliability, contractual posture), not a full specification of that reasoning; (2) No safe error margin: underestimate = contractual loss, overestimate = lost bid, no safe autonomous failure mode. Right = the new direction: RFQ Lifecycle Intelligence — control, evidence, coordination, learning around estimation. Don't name "Itqān" here — that's 02.2's reveal. Don't frame this as anti-AI — frame it as a positioning decision: human authority on estimation, platform authority on lifecycle. Four foundations orbit the central core, each carried by a dedicated microservice boundary: rfq_manager_ms (operational backbone), rfq_intelligence_ms (structured evidence), rfq_copilot_ms (bounded copilot), rfq_ui_ms + IAM (platform experience). High-level system shape — three layers: entry (UI), access (IAM, future seam), and three backend services. rfq_manager_ms owns operational lifecycle truth and is the backbone (visually emphasized so the role is felt, then drilled into at 03.2.a). rfq_intelligence_ms = structured evidence around workbooks and MR packages. rfq_copilot_ms = bounded conversation with safe answers and manager context. Each backend owns its own data store; manager's two stores (Operational DB + File storage) sit directly beneath it. Azure OpenAI is consumed by intelligence + copilot — explicitly not by manager. File storage is local today; Azure Blob is the planned target. IAM is a future seam, not yet implemented.

Backup · BACAB Internal Pattern

Each backend follows the same BACAB-inspired internal pattern.

HTTP request ↓
Routes thin
Controllers own decisions
Datasources · Connectors do not decide
Translators
API shape ↕ internal shape
Support · Models · Config · Utils · app_context

Each service follows the same BACAB-inspired structure. Routes are thin. Controllers contain the business decisions. Datasources handle storage. Connectors isolate external calls. Translators separate API shape from database or internal shape. This keeps the platform maintainable and testable.

Backup · Stage Transition Gates

A stage advances only after the manager validates the transition.

Current stage
Estimation
progress 80% · 2 notes · 1 file
→
Gate checks
01 Mandatory fields ✓
02 No active blockers ✓
03 Transition valid ✓
→
Atomic update
close current activate next current_stage_id timestamps progress recalculated
→
Next stage
Validation
opens when all gates pass
A stage advances only when three checks pass: required fields are complete, there are no active blockers, and the transition itself is valid. On success, an atomic update closes the current stage, activates the next, updates current_stage_id, writes timestamps, and recalculates RFQ-level progress.
