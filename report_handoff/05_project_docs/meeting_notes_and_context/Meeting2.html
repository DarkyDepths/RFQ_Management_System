01

Distinction API Resources vs. Entités du Modèle de Données

Principe Ressources exposées vs. entités internes

Les ressources API peuvent refléter le modèle de données mais ne le doivent pas nécessairement. Il existe des entités intermédiaires qui n'exposent pas de CRUD — elles sont construites à la demande en interne. Exemple : la création d'une RFQ via l'API déclenche en arrière-plan l'instanciation du stage initial et d'autres enregistrements. Le client n'interagit jamais directement avec ces entités intermédiaires.

Lorsqu'on parle de « ressources API », il s'agit exclusivement des ressources exposées au client de l'API. C'est avec ces ressources que l'on construit le contrat d'interface.

02

Approche Front-to-Back : Du Besoin Métier vers le Technique

Principe Migration du front vers le back

Dans la conception des microservices et des endpoints, l'approche adoptée est du besoin métier vers le technique, et non l'inverse. On part de l'interface front, on découpe en microservices, et pour chaque MS on définit les endpoints et les CRUD. C'est la première phase.

Décision Retrait de RFQ_Blocker en V1

Le concept de RFQ_Blocker est reconnu comme potentiellement valide mais il relève d'une démarche technique vers le métier. Pour la V1, on privilégie la simplicité : remplacement par un champ notes (objet JSON) dans l'entité rfq_stage pour les commentaires, et utilisation des reminders pour le suivi des dépassements.

Principe Méthodologie de travail

Besoin métier → Prototypage → Préparation des microservices front et back → Découpage du back → Swagger → Implémentation. Ce réflexe s'applique à tout projet.

03

Normes de Nommage des URI

Norme Convention de nommage

Le path (partie après l'adresse IP et le port) constitue l'URI. Le premier préfixe doit être le nom du microservice — et non simplement « api » — car chaque MS possède sa propre API. Le nom de la ressource dans l'URI doit correspondre au nom de la ressource de manière cohérente.

/{nom_microservice}/{version}/{nom_ressource}/{id_ou_action}
04

Architecture des Reminders

Décision Création vs. Exécution

La création des reminders se fait au niveau de rfq_manager_ms (c'est une ressource API avec CRUD). L'exécution des reminders est un processus batch.

Deux types identifiés : reminders internes (alertes équipe — remplace la fonctionnalité blocker) et reminders externes (alertes fournisseurs — suivi des réponses).

Décision Deux mains, un domaine

Étant donné la forte cohésion entre les reminders et les données RFQ, la solution retenue est un seul microservice avec deux points d'entrée : un « main » qui expose l'API REST (pour le front) et un « main » qui lance le batch des reminders. Les deux mutualisent la même couche domaine (logique métier et accès aux données), évitant ainsi les appels REST redondants et la duplication de code.

Retex Leçon apprise — Base de données partagée

Retour d'expérience BACAB : sur un projet antérieur, deux microservices accédaient à la même table de base de données. Un changement de schéma impactait les deux services. Règle établie : un microservice = une base de données. Ne jamais partager de tables entre services.

05

Architecture Hexagonale

Principe Architecture de référence BACAB

L'architecture hexagonale (Ports & Adapters) est l'architecture de référence utilisée. La couche « controller » (dans la terminologie BACAB) contient les règles métier et l'implémentation métier. L'exposition change (REST, batch, etc.) mais le domaine reste identique. Cela permet de mutualiser le domaine et d'éviter la redondance.

06

Cadrage de la Version 1

Décision Périmètre V1

Préparer une première version pour le PFE. Pour la V1 : uniquement les éléments structurants et les attributs qui seront certainement présents. Le modèle de données va évoluer — on investit uniquement dans ce qui est certain.

Le contexte ne dispose pas d'un cahier des charges figé et rigide. Des itérations (allers-retours) sont prévues jusqu'à obtenir une version finale.

Éléments reportés : Architecture event-driven (reconnue mais hors périmètre V1). Concept RFQ_Blocker (potentiellement valide, reporté à une itération future).

07

Principe de Cohésion — Ne Pas Sur-Découper

Principe Cohésion métier

Diviser excessivement et avoir plusieurs microservices peut être un inconvénient et non un avantage. L'objectif n'est pas d'avoir de nombreux microservices. Il faut toujours examiner la logique métier et la cohésion pour décider de regrouper ou de séparer. Ne pas tomber dans la redondance et la double/triple maintenance.
