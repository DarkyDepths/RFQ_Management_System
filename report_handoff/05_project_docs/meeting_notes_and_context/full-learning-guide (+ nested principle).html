Chapter 1

Database Entity vs. API Resource

A database entity is a table in your database. It stores data. rfq, rfq_stage, workflow — those are entities with columns and relationships.

An API resource is something you deliberately expose to the outside world (the front-end). It's a door you open for the client to interact with.

Core Rule

Not every database entity becomes an API resource. Some entities are intermediate — they exist in the database but are never exposed. They're created behind the scenes when another resource is created.

TypeWhat it isExample
API Resource + EntityExposed to front-end AND stored in DBrfq — users create and view RFQs
Entity only (intermediate)Stored in DB, never exposed directlyrfq_stage records auto-created when an RFQ is created
API Resource only (computed)Exposed to front-end but NOT a table/rfqs/stats — computed from multiple tables

A restaurant menu (API) lists "Pasta Carbonara" — one item the customer can order. In the kitchen (database), making that dish involves boiling water, cooking bacon, whisking eggs, preparing sauce — multiple operations. The customer never says "please boil water." That's an internal operation.

The Test

Ask: "Does the front-end need to directly create, read, update, or delete this thing?"

If yes → API resource. If no → intermediate entity (internal only).

Important Nuance

An entity like rfq_stage can be both intermediate AND an API resource depending on context. The creation of stages is intermediate (auto-created behind POST /rfqs). But viewing and updating a stage is exposed (the workspace needs GET and PATCH on stages). The front-to-back approach tells you which operations to expose.

Chapter 2

RESTful API Design

REST is the language your front-end and back-end use to communicate over HTTP. It has two parts: resources (the things) and methods (the actions).

HTTP Methods = CRUD

MethodActionMeaning
POSTCreate"Make a new one"
GETRead"Give me one" or "Give me all"
PUTReplace"Replace this entirely with new data"
PATCHPartial update"Update just some fields"
DELETEDelete"Remove this one"

Combining Methods + Resources

POST /rfq-manager/v1/rfqs → Create a new RFQ GET /rfq-manager/v1/rfqs → List all RFQs GET /rfq-manager/v1/rfqs/42 → Get RFQ number 42 PATCH /rfq-manager/v1/rfqs/42 → Update some fields of RFQ 42 DELETE /rfq-manager/v1/rfqs/42 → Delete RFQ 42

Custom Actions

Sometimes CRUD isn't enough. Advancing a stage isn't just "updating" it — it's a business operation with side effects. Custom actions go at the end of the path:

POST /rfq-manager/v1/rfqs/42/stages/5/advance → Complete stage, move forward POST /rfq-manager/v1/reminders/test → Send a test email

Query Parameters = Filters

When you need to filter or search, you add query parameters with ? and join them with &:

GET /rfq-manager/v1/rfqs?status=open&workflow=long&search=aramco → "Give me RFQs that are open, use long workflow, and match 'aramco'"
Key Rules

Never put verbs in the URL. /createRfq is wrong — the method (POST) is the verb. Resource names are always plural and lowercase: /rfqs not /rfq or /Rfqs.

Chapter 3

URI Naming Conventions

BACAB's naming standard:

/{microservice_name}/{version}/{resource_name}/{id_or_custom_action}

A full URL with the URI:

https://192.168.1.10:8080/rfq-manager/v1/rfqs/42 |_________________________||___________________________| URL base URI (IP + port) (the path part)

Why prefix with the microservice name instead of just /api? Because if you have 6 microservices and they all start with /api/, it's confusing. The MS name creates a clear namespace — you always know which service you're calling.

Examples from RFQMGMT: /rfq-manager/v1/rfqs → RFQ manager service /rfq-manager/v1/workflows → RFQ manager service /rfq-chatbot/v1/conversations → Chatbot service /rfq-iam/v1/users/me → IAM service
Chapter 4

Front-to-Back Design Approach

This is BACAB's core philosophy. The approach is: business need → technical solution, never the reverse.

Wrong Approach (Back-to-Front)

Start from database → design entities → create endpoints for each → hope the front-end needs them.

This is how RFQ_Blocker happened: a technical solution built before a business need was confirmed.

Right Approach (Front-to-Back)

Start from UI → identify user actions → those become API resources → design the data model to support them.

This is how Subtasks and File attachments were discovered — the UI showed them, so they're needed.

The Workflow

UI Mockups → User Actions → API Resources → Data Model → Swagger → Implementation What do users What can they What endpoints What tables Formalize Write see on screen? do? (click, serve these support the contract the code view, fill) actions? these APIs?
What "Viewing" Means

A user viewing data on a page IS an interaction. The user opens the page, and the front-end automatically calls the API to fetch data. Any data displayed on screen that comes from the server requires a GET endpoint. You don't need a button click — the page load itself triggers the API call.

Chapter 5

Nested vs. Top-Level Resources

This determines whether a resource gets its own independent endpoints or lives under a parent resource in the URI.

The Test

"Can the user access this thing independently, across all parents?"

If yes → Top-level resource (own base endpoint)

If no, it only makes sense inside a specific parent → Nested resource

Evidence from the UI

ResourceHow users access it in the UIResult
ReminderTasks page shows "all my reminders across all RFQs" globallyTop-level: /reminders
WorkflowAdmin page lists all workflows independently, before any RFQ existsTop-level: /workflows
StageUser always picks an RFQ first, then sees its stagesNested: /rfqs/{id}/stages
SubtaskUser goes RFQ → Stage → then sees subtasksNested: /rfqs/{id}/stages/{stageId}/subtasks
FileFiles always belong to a specific stage of a specific RFQNested: /rfqs/{id}/stages/{stageId}/files
Important

The database structure doesn't decide the nesting. You might have an rfq_stage table in the database — that's fine. But the API doesn't expose it as /stages independently because no UI flow needs "show me all stages across all RFQs." The way the user accesses data decides the nesting.

Common Mistake

Modeling an entity in the database and automatically assuming it gets its own independent endpoints. Having an rfq_stage table does NOT mean you need GET /stages. The entity exists in the DB, but the API resource is nested because that's how users access it.

Chapter 6

Hexagonal Architecture (Ports & Adapters)

BACAB's standard architecture. The core idea: your business logic sits in the center and is protected from the outside world.

┌──────────────────────────────────────┐ │ ADAPTERS (outer ring) │ │ REST API | Batch Job │ ← How you talk to the world │ │ │ ┌────────────────────────────────┐ │ │ │ PORTS (middle ring) │ │ ← Interfaces / contracts │ │ │ │ │ │ ┌──────────────────────────┐ │ │ │ │ │ DOMAIN (center) │ │ │ ← Business rules │ │ │ │ │ │ │ │ │ getOverdueRfqs() │ │ │ │ │ │ createRfq() │ │ │ │ │ │ checkDeadlines() │ │ │ │ │ └──────────────────────────┘ │ │ │ └────────────────────────────────┘ │ └──────────────────────────────────────┘

Domain (center) — the business logic. "How do I create an RFQ? When is an RFQ overdue?" These rules never change regardless of who's calling.

Ports (middle) — interfaces that define what the domain can do. A menu of capabilities.

Adapters (outer) — the different ways to access the domain. REST adapter for HTTP. Batch adapter for scheduled jobs. Both use the same domain.

Without Hexagonal (the problem)

❌ Business logic MIXED into REST code app.get('/rfqs/overdue', (req, res) => { const rfqs = db.query("SELECT * FROM rfq WHERE deadline < NOW()"); res.send(rfqs); }); ❌ Batch needs same logic? Copy-paste! schedule('8am', () => { const rfqs = db.query("SELECT * FROM rfq WHERE deadline < NOW()"); sendEmails(rfqs); }); → Two places to maintain. Rule changes? Update both. Forget one? Bug.

With Hexagonal (the solution)

✅ Business logic in the DOMAIN (one place) function getOverdueRfqs() { return db.query("SELECT * FROM rfq WHERE deadline < NOW()"); } ✅ REST adapter — thin, just calls domain app.get('/rfqs/overdue', (req, res) => { res.send(getOverdueRfqs()); }); ✅ Batch adapter — thin, just calls domain schedule('8am', () => { sendEmails(getOverdueRfqs()); }); → Rule changes? Update once. Done.
The Reflex

You don't "choose" hexagonal in specific situations. You always keep business logic separate from how it's accessed. The architecture emerges from one discipline: business logic never lives inside an adapter.

Chapter 7

Batch Processing & Two Mains

REST vs. Batch

REST EndpointBatch Process
TriggerSomeone asks (HTTP request)Clock fires (scheduled)
WhenOn demandAutomatically (e.g., daily at 8 AM)
ExampleUser clicks "Load RFQ"System checks reminders, sends emails

The Two Mains Pattern

Reminders need RFQ data. Two options:

Option A — Separate MS (problematic)

Reminder batch as a separate microservice. Calls rfq_manager via REST for data. Extra overhead, extra network calls, another service to deploy.

Option B — Two Mains (BACAB's choice)

One microservice, two entry points. Main 1 starts the REST server. Main 2 starts the batch scheduler. Both share the same domain layer. No redundant calls, no duplicated code, one database.

rfq_manager_ms ├── Main 1: REST Adapter → Front-end calls come in here ├── Main 2: Batch Adapter → Reminder scheduler runs here │ └── Both share the SAME DOMAIN: ├── listOverdueRfqs() ├── getRfqDetails() └── checkDeadlines()

A building with two doors — a front door (REST API for the UI) and a back door (batch for reminders). Both doors lead to the same rooms inside (the domain layer). You don't need a second building and then shout across the street for information.

BACAB Lesson Learned

In a previous project, two microservices shared the same database table. When one changed the schema, it broke the other. Rule: one microservice = one database. Never share tables between services.

Chapter 8

Business Logic & the Domain Layer

Business logic is the rules specific to your project's real-world problem — how GHI actually works.

What happens when a new RFQ is created? When is an RFQ overdue? Can a stage be skipped? What data is required before submission? When should a reminder fire?

These rules come from how GHI works — not from technology. If GHI used paper and filing cabinets, these rules would still exist.

Business Logic (domain)NOT Business Logic (adapters)
Creating an RFQ and auto-generating stagesReceiving an HTTP request
Calculating if an RFQ is overdueRunning a job at 8 AM
Checking mandatory fields before advancingSending back a JSON response
Determining which team owns a stageConnecting to the database
The Principle

Business logic is the what and why. Adapters are the how and when. The domain doesn't know or care who's calling it.

Chapter 9

Swagger / OpenAPI

Swagger is the blueprint you write before coding. It's the formal contract between front-end and back-end.

For each endpoint it defines: what URI, what HTTP method, what data goes in (request), what data comes back (response), and what errors can happen.

Example: simplified Swagger for RFQ creation POST /rfq-manager/v1/rfqs Input: { title, client, industry, country, priority, deadline, owner, description, workflow_id } Output: { id, title, client, status, current_stage, created_at } Errors: 400 Bad Request 401 Unauthorized
Why It Matters

Once Swagger is agreed on, front-end and back-end work in parallel. The front-end knows what to send and expect. The back-end knows what to build. Nobody waits. This is the "interface contract."

Chapter 10

Guiding Principles

The rules that govern every decision — from everything your bosses said.

Principle 1 — Front-to-Back, Always

Start from the business need (UI) and work toward the technical solution (database). Never the reverse. The UI decides what gets exposed. The data model supports it.

Principle 2 — One Microservice = One Database

Never share database tables between services. If two things need the same data and share many entities, they probably belong in the same microservice.

Principle 3 — Don't Over-Split

More microservices ≠ better. Every new MS means a new database, deployment, monitoring, and API contracts. Split only when there's a clear difference in business cohesion.

Principle 4 — V1 = Strictly Necessary

Only structuring elements and attributes that will definitely be present. The model will change — don't over-invest in uncertain details. Iterate until reaching a final version.

Principle 5 — No Redundancy

Don't fall into double and triple maintenance. Use hexagonal architecture to share the domain layer. Design one endpoint and let multiple pages reuse it. One API, multiple consumers.

The Complete Workflow — Applies to Any Project

1. Look at the UI mockups — what can the user see and do?

2. Map those actions to API resources and endpoints

3. Adjust the data model to support those endpoints

4. Build the Swagger contract (formalize the interface)

5. Start implementation (controllers, routes, connectors)
