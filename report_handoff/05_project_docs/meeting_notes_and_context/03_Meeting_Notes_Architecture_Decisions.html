01 — Core Concept

API Resources ≠ Database Entities

Key What They Said

API resources can reflect a data model — but they don't have to. There are entities in the data model that will never be exposed as endpoints. When you create an exposed resource like RFQ, behind the scenes it triggers creation of multiple database records (e.g., instantiation of an initial RFQ stage). These intermediate entities are "built on demand" — the client never interacts with them directly.

When we talk about "API resources," we mean the resources you expose to the client of your API.

Think of a restaurant: the menu is your API (what the customer sees and orders). The kitchen is your database (where multiple things happen to prepare one dish). The customer orders "Pasta Carbonara" (one API call). Behind the scenes, the kitchen boils water, cooks bacon, whisks eggs, prepares sauce — multiple operations from one order. The customer never says "please boil water" — that's an internal operation. Same idea: RFQ is on the menu, but rfq_stage creation is a kitchen operation.

02 — Core Philosophy

Front-to-Back: Business Need → Technical Solution

Key What They Said

In microservice design and endpoint design, we migrate from the front to the back — from the business need to the technical. Our approach is NOT technical → business, it's the complete opposite. You take the front-end, you break it into microservices, and for each MS you list the endpoints and CRUDs. That's phase 1.

Decision RFQ_Blocker Feedback

Your idea is good, but we want to be simpler in V1. RFQ_Blocker is potentially an extraordinary solution, but for a business problem that we define first — not the other way around. We don't try to add problems to existing problems even if the solution is valid. It may have its time later. For now, replace it with a notes field (JSON object) in the rfq_stage entity for comments, and use reminders to handle deadline overruns.

You proposed RFQ_Blocker thinking "this would be a useful feature, let me model it." They want you to flip that: start from "what does the user need to do on the screen?" and then figure out the minimal technical solution. The blocker concept was a solution looking for a problem. A simple notes field + reminders covers the actual V1 need.

03 — Standards

URI Naming Conventions

Learn What They Said

The path (after the IP address and port) is the URI. The first prefix must be the microservice name — not just "api" — because every MS has its own API. The resource name in the URI must match the actual resource name consistently.

/{microservice_name}/{version}/{resource_name}/{id_or_custom_action}

Example:
/rfq-manager/v1/rfqs → List all RFQs
/rfq-manager/v1/rfqs/{id} → Get specific RFQ
/rfq-manager/v1/rfqs/{id}/submit → Custom action on RFQ
/rfq-manager/v1/reminders → List reminders
/rfq-manager/v1/reminders/{id} → Get specific reminder

If you use just /api/v1/rfqs, and you have 6 microservices, they'd all start with /api/ — confusing. By prefixing with the MS name, every service has its own clear namespace. The gateway or front-end knows exactly which service they're calling.

04 — Architecture Decision

Reminders: Creation vs. Execution

Decision What They Said

Reminder creation = inside rfq_manager_ms (it's an API resource — you CRUD reminders). Reminder execution = a batch process. The reminder has a strong cohesion with RFQ data (it needs to list RFQs, check deadlines, etc.).

Two types: internal reminders (replaces blocker — team alerts about stuck RFQs) and external reminders (replaces supplier follow-up — alerts about suppliers not responding).

Key The Shared Database Lesson

BACAB made this mistake before in another project: two microservices accessing the same database table. When one changed the schema, it broke the other. Rule: one microservice = one database. Never share tables between services.

Decision Two Mains, One Domain

Since reminders need RFQ data and share entities with rfq_manager, the solution is: one microservice with two entry points. Main 1 exposes the REST API (for the front-end). Main 2 runs the batch (for reminders). Both share the same domain layer (business logic + data access). This avoids redundant REST calls and code duplication.

Imagine a building with two doors — a front door (REST API for the UI) and a back door (batch process for reminders). Both doors lead to the same rooms inside (the domain layer — your business logic). You don't need to build a second building and then shout across the street to ask for information. The two "mains" pattern means one codebase, one database, two ways to enter.

05 — Learn This

Hexagonal Architecture (Ports & Adapters)

Learn What They Said

Research hexagonal architecture. At BACAB, the "controller" layer contains business rules and implementation. The exposure changes but the domain stays the same. This is how you mutualize the domain and avoid redundancy. This is the architecture they use.

Hexagonal architecture says: put your business logic in the center (the "domain"). Around it, create "ports" (interfaces) and "adapters" (implementations). A REST adapter handles HTTP requests. A batch adapter handles scheduled jobs. A database adapter handles persistence. They all connect to the same core domain. If you swap the REST adapter for a GraphQL adapter tomorrow, the domain doesn't change. In your case: the REST adapter serves the front-end, the batch adapter runs reminders — both use the same domain logic for accessing RFQs, checking deadlines, etc.

06 — Guiding Principle

V1 = Strictly Necessary, Iterations Expected

Key What They Said

We must prepare a first version for the PFE, then we can add. But right now, we define what to deliver. For V1, we put the structuring elements and attributes that will definitely be present. The model will change — so for V1, only what's certain.

When the spec is not fixed and rigid, and the client doesn't know exactly what they want (which is our context), we don't have a single phase — we do back-and-forth iterations until reaching a final version.

Event-driven architecture — they acknowledged you designed it but it's not in the V1 scope. Don't invest time here now.

✓ What They Appreciated

Your entity modeling and the relationships between entities (FK/PK pointers between different entities). They said you need to perfectly master these links and references.

07 — Don't Over-Split

More Microservices ≠ Better

Key What They Said

Splitting too much and having too many microservices can be a disadvantage, not an advantage. The objective is not to have many microservices. Always look at business logic and cohesion to decide what goes in the same MS or gets separated. Don't fall into redundancy and double/triple maintenance. One microservice = one database.

Every time you create a new microservice, you're creating: a new database, a new deployment pipeline, new monitoring, new API contracts between services, new failure points. If two things are tightly related (like reminders and RFQs), putting them in separate services means they constantly need to call each other — that's overhead, not architecture. Group by business cohesion, split only when the domains are truly independent.
