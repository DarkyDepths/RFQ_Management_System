4 Concepts Before You Code

Everything you'll write in this project uses these 4 concepts. Nothing else is new — the rest is your business logic organized into BACAB's layers.

Concept 1

Python Generators & yield

Give something, pause, clean up after.

The problem

You need to give a database session to a route, let the route use it, then close it when done — even if the route crashes. return can't do this because the function dies after returning.

return vs yield

✗ return — function dies
def get_session():
    session = open_session()
    return session
    # ← function is DEAD
    # nobody closes the session
✓ yield — function pauses
def get_session():
    session = open_session()
    yield session
    # ← PAUSED — route works
    session.close()
    # ← RESUMES — cleanup runs

How it works step by step

Lifecycle of yield
① open session
↓
② yield session → PAUSE
↓
③ route uses the session (reads, writes, etc.)
↓
④ route finishes → RESUME
↓
⑤ close session — cleanup

The real version (with crash safety)

try/finally ensures cleanup always runs, even if the route throws an error.

def get_db():
    session = SessionLocal()
    try:
        yield session          # pause — request runs
    finally:
        session.close()        # ALWAYS runs, success or crash

yield = "give this, wait, then clean up."

Concept 2

Pydantic & Data Validation

Describe the shape of data, reject anything that doesn't match.

The problem

A user sends JSON to create an RFQ. It could be perfect — or it could be missing fields, wrong types, or completely garbage. You need to catch this before it reaches your controller or database.

✓ Valid request
{
  "client_name": "Saudi Aramco",
  "project_name": "Heat Exchanger",
  "deadline": "2026-06-15",
  "workflow_id": "abc-123"
}
✗ Invalid request
{
  "client_name": "",
  "deadline": "not-a-date"
  // missing project_name
  // missing workflow_id
}

The solution — define the shape

You create a Python class that describes exactly what you expect:

from pydantic import BaseModel
from datetime import date

class RfqCreateRequest(BaseModel):
    client_name: str                   # required string
    project_name: str                  # required string
    deadline: date                     # required, must be a valid date
    workflow_id: str                   # required string
    priority: str = "Medium"           # optional — defaults to "Medium"
    description: str | None = None     # optional — can be absent

How FastAPI uses it

Automatic validation flow
JSON body arrives
→
Pydantic validates
→
Valid? → route runs
JSON body arrives
→
Pydantic validates
↘
Invalid? → 422 error (route never runs)
# In your route:
@router.post("/rfqs")
def create_rfq(body: RfqCreateRequest):
    # If you reach this line, data is ALREADY valid
    # body.client_name → string ✓
    # body.deadline → date object ✓
    # Missing field? → FastAPI sent 422, this never runs

Where this lives in your project

Pydantic schemas go in translators/. Each resource has request schemas (what comes in) and response schemas (what goes out). FastAPI uses request schemas to validate input, and response schemas to format output + auto-generate Swagger docs.

Pydantic = "define the expected shape, let FastAPI reject the rest."

Concept 3

SQLAlchemy — Engine, Session, Base

Three things, three jobs. Each one has a different role.

The big picture

How Python talks to PostgreSQL
FastAPI (your app)
↓
Session (one conversation per request)
↓
Engine (the connection — created once)
↓
PostgreSQL (the database)

① Engine — the connection

Created once when the app starts. It holds the database URL and manages a pool of connections. Think of it as the highway — you build it once, every car uses it.

from sqlalchemy import create_engine

engine = create_engine("postgresql://user:pass@localhost/rfq_db")

You never touch the engine directly after this. It works in the background.

② Base — the table registry

Every database table you define inherits from Base. This is how SQLAlchemy knows "this Python class = a database table."

from sqlalchemy.orm import declarative_base

Base = declarative_base()

class RFQ(Base):                     # "I am a database table"
    __tablename__ = "rfq"
    id = Column(UUID, primary_key=True)
    client_name = Column(String(200))

class Workflow(Base):                # "I am also a database table"
    __tablename__ = "workflow"
    id = Column(UUID, primary_key=True)
    name = Column(String(100))
What Alembic sees
Base
→
"Who are my children?"
→
RFQ, Workflow, RFQ_Stage ...

Alembic asks Base for all its children and generates CREATE TABLE SQL for each one. If a model doesn't inherit from Base, Alembic won't see it.

③ Session — one conversation per request

The session is where you actually read and write data. It collects everything you want to do, then sends it all at once when you commit().

session = SessionLocal()               # start a conversation

rfq = RFQ(client_name="Aramco")
session.add(rfq)                        # "I want to insert this" (NOT sent yet)

stage1 = RFQStage(rfq_id=rfq.id)
session.add(stage1)                     # "Also insert this" (still NOT sent)

session.commit()                        # NOW send everything — one transaction
session.close()                         # conversation over

Why this matters for transaction safety: When you create an RFQ and auto-create its 5 stages, you call session.add() for each one but only session.commit() once. If stage 3 fails → session.rollback() undoes everything. No partial state. The RFQ and stages 1–2 are also gone.

How they connect

One-time setup vs per-request
Engine
created once at startup
↓ bound to
SessionLocal
factory — knows how to create sessions
↓ creates
session
one per request — reads/writes/commits
↓ uses
Models (inherit from Base)
know what tables and columns exist

Engine = the road. SessionLocal = car factory. Session = one car per request. Base = map of destinations.

Concept 4

Dependency Injection & Depends()

Don't create it yourself — let FastAPI provide it.

The problem

Without dependency injection, every route creates its own objects:

# ✗ WITHOUT dependency injection — repeated in every route
@router.post("/rfqs")
def create_rfq(body: RfqCreateRequest):
    session = SessionLocal()             # create session myself
    datasource = RfqDatasource(session)  # create datasource myself
    controller = RfqController(datasource)# create controller myself
    result = controller.create(body)
    session.close()
    return result

28 endpoints × 3 lines of setup = 84 lines of duplicated wiring. And if you change how sessions are created, you change it in 28 places.

The solution — Depends()

You tell FastAPI: "when a route asks for X, here's how to provide it."

# ✓ WITH dependency injection — route receives what it needs
@router.post("/rfqs")
def create_rfq(body: RfqCreateRequest, ctrl = Depends(get_rfq_controller)):
    return ctrl.create(body)   # one line — that's it

Depends(get_rfq_controller) means: "before running this route, call that function and give me what it returns." The route never creates anything itself.

How the chain works

Your route needs a controller. The controller needs a datasource. The datasource needs a session. You build this chain with multiple Depends():

# Datasource depends on session
def get_rfq_datasource(db = Depends(get_db)):
    return RfqDatasource(db)

# Controller depends on datasource
def get_rfq_controller(ds = Depends(get_rfq_datasource)):
    return RfqController(ds)

# Route depends on controller
@router.post("/rfqs")
def create_rfq(body: RfqCreateRequest, ctrl = Depends(get_rfq_controller)):
    return ctrl.create(body)
FastAPI resolves the chain backwards
Route needs → controller
↓ calls get_rfq_controller
Controller needs → datasource
↓ calls get_rfq_datasource
Datasource needs → session
↓ calls get_db
get_db yields → session

FastAPI walks the chain, creates everything bottom-up, and hands the final controller to the route. When the request ends, get_db resumes and closes the session (Concept 1).

Where this lives in your project

All the get_*_datasource and get_*_controller functions live in app_context.py. That's the single file where the entire dependency chain is defined for all 6 resources. Routes just import what they need:

# routes/rfq_route.py
from src.app_context import get_rfq_controller

@router.post("/rfqs")
def create_rfq(body: RfqCreateRequest, ctrl = Depends(get_rfq_controller)):
    return ctrl.create(body)

Why this matters for transactions: FastAPI calls get_db() once per request. That same session gets passed to every datasource. So when the RFQ controller calls rfq_datasource.insert() AND rfq_stage_datasource.insert() five times — they all share the same session. One commit(), one transaction, one rollback if anything fails.

Depends() = "don't create it yourself, let FastAPI wire it." app_context.py = the wiring diagram.
