Section 01

The Core Shift

From chatbot-centric to intelligence-first architecture.

Architectural Principle
The chatbot is the interface to intelligence,
not the owner of intelligence.
In the old model, intelligence lived inside chatbot tools — the LLM decided what to call and how to reason. In the new model, intelligence is a shared platform capability that serves multiple consumers — the UI, the chatbot, dashboards, workflow-driven alerts, and intelligence's own learning loop. The chatbot becomes a thin conversational layer that navigates, explains, and extends intelligence it does not own.
Operational Engine

rfq_manager_ms

Owns the RFQ lifecycle — workflows, stages, business transactions, operational state. Owns "today." Already built and working (Phases 1–4).

Intelligence Engine

rfq_intelligence_ms

Owns parsing, historical matching, cost analysis, supplier intelligence, KPI analytics, and the structured historical database. Owns "memory and insight." The primary value driver for GHI.

Conversational Layer

rfq_chatbot_ms

Owns conversation sessions, intent detection, context resolution, response wording, and UX. Consumes intelligence — never produces it. Intentionally thin.

Why This Separation Is Not Optional

Intelligence in the GHI platform has multiple distinct consumers, not just the chatbot. In the old BACAB pattern, the chatbot was the only entry point — so embedding intelligence inside chatbot tools was acceptable. In GHI, that is no longer true. Locking intelligence inside chatbot tools would force every other consumer to route through a fake conversation — a structurally wrong pattern.

Consumer Layers — Ordered by V1 Concreteness

V1 Concrete — Built and Integrated

UI / RFQ overview screens: display the intelligence briefing panel, anomaly flags, and reference data directly in the interface.
Chatbot (rfq_chatbot_ms): navigates, explains, and extends intelligence conversationally.
BI / Dashboard views: consume aggregate analytics — KPIs, pipeline funnel, win rates, margin trends.

V1 Present but Lighter

Event-driven workflow consumers: intelligence produces signals (anomaly alerts, compliance flags, risk scores) that workflow logic inside rfq_manager_ms can consume for warnings and alerts. This is not the stage-advancement logic — it is intelligence enriching the context around the lifecycle.

Future / Embedded for Now

Communication capabilities: currently owned by rfq_manager_ms (reminders, follow-ups). May consume intelligence context — client history, supplier signals — for smarter drafting and escalation. Remains internal to manager for now; may become a dedicated service later.

Self-Enrichment — Always Active

Intelligence's own historical store: every parsed RFQ, every workbook extraction, every recorded outcome enriches the analytical database. Intelligence is simultaneously a producer and a consumer of its own outputs. This creates a continuous learning loop without retraining — the platform gets smarter by existing.

Additionally, much of the intelligence workload is system-triggered, not user-triggered. Parsing new RFQ documents, enriching historical memory, comparing live estimates against historical patterns, generating benchmarking signals — none of these are chatbot conversations. They are background processes that produce persistent intelligence artifacts consumed later by humans and systems alike.

These are the main initial consumers, not necessarily the final exhaustive list. The architecture is designed so that new consumers can be added without modifying the intelligence engine — they simply call its APIs or subscribe to its events.

Section 02

Three Operating Modes

Intelligence is not a single behavior. It operates in three fundamentally different modes with different triggers, outputs, and consumers.

Mode 1 — Proactive

Activates automatically on system events, without anyone asking.

Triggers: New RFQ registered with documents attached. Estimation workbook uploaded or updated. RFQ outcome recorded (won/lost/declined). Stage transitions in the lifecycle.

Outputs: Intelligence Briefing dossier. Workbook validation and anomaly reports. Historical database enrichment. Feedback loop records for learning.

Consumers: UI (briefing panel on RFQ overview), workflow engine (alert triggers), historical database (self-enrichment).

This is the flagship mode. The "wow" moment for GHI: open a new RFQ and the system has already done homework for you.

Mode 1 outputs are persistent artifacts — briefings, validation reports, enrichment records — not temporary background calculations. Each artifact has a status, a timestamp, and a version. It can be queried by any consumer, re-generated when new data arrives, and tracked over time. That is what separates this from "the system ran a background task."

Mode 2 — Reactive

Responds to explicit queries from consumers.

Triggers: Chatbot passes a user question. Dashboard requests KPI computation. Other services call intelligence APIs for specific analysis.

Outputs: Structured JSON responses — similar projects, cost ranges, supplier profiles, analytics results. Always structured data, never raw conversation text.

Consumers: rfq_chatbot_ms (primary), BI dashboards, and any service that needs structured intelligence data on demand.

Mode 3 — Aggregate

Serves portfolio-level analytics across many RFQs over time.

Triggers: Dashboard loads. Scheduled KPI refresh. Leadership requests performance review.

Outputs: Win rate trends by client/type/period. Margin drift analysis. Department bottleneck patterns. Pipeline risk distribution. Estimation accuracy tracking. Client profitability segmentation. Capacity utilization.

Consumers: Executive BI dashboards, C-suite reports, department performance views.

This mode is fundamentally different from per-RFQ analysis — it works across the entire portfolio. The data access patterns, query shapes, and consumers are distinct. Housed in the same service, but a separate capability block internally.

Mode 3 directly addresses Pillar 3 — Executive Intelligence & BI from the GHI audit, and pain point PP-03 (zero executive visibility). Today, Albassam leadership has no real-time view of their RFQ pipeline, win rates, or margin performance. Mode 3 is how the platform closes that gap — the same intelligence engine that helps estimators also powers the dashboards that give C-suite full visibility.

Section 04

The Intelligence Briefing

The flagship proactive output — a structured dossier generated automatically the moment an RFQ enters the system.

When a new RFQ is registered and documents are attached, rfq_intelligence_ms automatically produces a briefing — a structured analytical dossier that is ready before the first human opens the RFQ. This is the platform's primary "AI moment" for GHI. No one asks for it. It's just there.

Briefing Contents

Section A — Document Understanding

Extracted from the MR package: vessel types, quantities, dimensions, material grades, applicable standards (ASME, TEMA, FATI, SAMSS, SAES, SAEP), mandated vendors (from RVL folder), scope of supply, QA/QC requirements.

Section B — Similar Past Projects

Top N historical RFQs matching the extracted characteristics. Ranked by similarity score. Each match shows: scope, tonnage, material, cost-per-ton, margin, outcome (won/lost), delivery timeline.

Section C — Preliminary Cost Envelope

3-scenario analysis (best/expected/worst) based on similar projects. Not a BOQ — a ballpark range. Shows cost-per-ton benchmarks, dominant cost drivers, and confidence level based on reference count.

Section D — Client Intelligence

History with this client: past win rate, average margins, typical turnaround, negotiation patterns, payment behavior. If new client, the system says so explicitly.

Section E — Compliance & Risk Flags

Auto-detected from folder structure and document content: required standards, mandated supplier constraints, PWHT requirements, U-Stamp / NB registration needs, and their historical cost implications.

Section F — Supplier Signals

For key materials identified: known supplier options, recent price trends, lead time history, reliability scores. Mandated vendors (from RVL) highlighted with availability context.

What Makes Two RFQs Similar — The Core Challenge

Similarity is the foundation of the intelligence engine. If the similarity logic is weak, then historical matching becomes weak, cost estimation becomes weak, and anomaly detection loses its reference baseline. This section defines what similarity means in concrete, domain-grounded terms — not as a vague AI concept, but as a weighted, explainable, layered comparison model.

Similarity is not one magical score. It is built from three distinct layers, and different consumers weight these layers differently depending on what they need.

Layer 1 — Technical / Product

Equipment or vessel type (horizontal, vertical, heat exchanger…). Material grade or family (SA 516 Gr. 70N, stainless, duplex…). Weight/tonnage range. Dimension range (ID × length). RT type (full/spot). PWHT (yes/no). U-Stamp / NB requirements. Number of items. Complexity signals from standards or QA/QC requirements.

This layer matters most for cost estimation — what you're building physically drives what it costs.

Layer 2 — Commercial / Execution

Client name and client segment. Delivery duration band. Payment and financial structure. Supplier constraints and RVL mandates. Project scale and scope boundaries.

This layer matters most for bid strategy — who you're bidding for and under what commercial conditions shapes win probability.

Layer 3 — Cost Behavior

Cost-per-ton band. Major cost-line proportions (material %, labour %, NDT %, overheads %). Margin band. Schedule intensity. Financial charge structure.

This layer matters most for anomaly detection — it defines what "normal" looks like for comparable projects.

Explainability requirement: When the system says "these 5 projects are similar," it must also say why — "matched on: horizontal vessel, SA 516 material, 8–15 ton range, full RT, same client." A bare "85% similar" score with no breakdown is not trustworthy and will not be used by GHI estimators. Every similarity result must be traceable to specific matching features.
Data sources for similarity features: Layer 1 and partial Layer 2 features can be extracted from the MR package at intake (vessel type, materials, standards, RVL, client). Full Layer 2 and all Layer 3 features require the estimation workbook. This means the briefing at arrival uses a partial similarity model (Layers 1 + partial 2), while post-workbook intelligence can use the full similarity model (all three layers). The system should be transparent about which layers were used in each comparison.

Discovering Similarity Weights — From Data, Not From Gut Feeling

A critical insight from the GHI context: the estimators themselves do not consciously compare projects. They treat each RFQ as a new exercise, rarely referencing past work. That means asking them "what makes two projects similar?" will not produce reliable weights — this knowledge does not exist in anyone's head. It has never been extracted because GHI has never analyzed their historical workbooks as a dataset.

This is not a limitation. This is the platform's unique value proposition. The intelligence engine does not encode existing expertise about similarity — it creates new knowledge that GHI has never had. The organization is sitting on 100+ completed workbooks, each one a rich structured data point, and nobody has ever looked across them for patterns.

What this means in practice: Similarity weights are not hand-tuned by interviewing estimators. They are discovered from historical data through statistical analysis and, as the dataset grows, through machine learning. The matching engine at query time stays deterministic and explainable. But the calibration behind it is data-driven — and that calibration is itself one of the platform's most valuable intelligence outputs.

Phase-by-Phase: How Similarity Weights Are Built

Phase 1 — Expert-Seeded Defaults

Before enough data exists

Start with reasonable initial weights based on domain common sense: vessel type and material grade are likely the strongest drivers, weight/tonnage range is important, compliance flags (PWHT, RT, U-Stamp) add meaningful cost, client has some influence.

These are starting assumptions, not validated truths. They are enough to produce useful (if imperfect) similarity results from the first day the system has historical data. They will be replaced as soon as statistical analysis becomes possible.

What to tell the bosses: "We start with sensible defaults so the system works immediately. But we don't trust them — we use data to find the real weights."

Phase 2 — Statistical Feature Importance

Once 50+ workbooks are parsed

With 50+ structured historical records, each row is a past RFQ and each column is a feature: vessel type, material, tonnage, item count, RT, PWHT, standards count, client. The target variables are cost-per-ton, margin, total cost, outcome.

Concrete techniques:

• Correlation analysis — which features correlate most with cost-per-ton? This answers: "does material grade matter more than vessel type?"

• Regression-based feature importance — fit a basic regression model predicting cost-per-ton from features. The coefficients show relative importance. With 50–100 data points and 15–20 features, this is statistically sound.

• Variance analysis — how much of the cost variance is explained by each feature group? "Vessel type + material explains 60% of cost variance; PWHT adds 12%."

Those percentages become the similarity weights — grounded in data, not gut feeling. The matching engine is updated to use data-derived weights instead of the Phase 1 defaults.

What to tell the bosses: "We analyzed your past 50+ projects and discovered that material grade and vessel type explain most of the cost variation. Now the system knows what to compare — and GHI knows something about their own business that they never knew before."

Phase 3 — Learned Similarity & Clustering

Once 100+ data points + outcomes exist

With a larger dataset, more sophisticated approaches become viable:

• Unsupervised clustering (k-means, hierarchical, DBSCAN) — discover natural project archetypes. Maybe 4–5 project families emerge that GHI doesn't explicitly name but that behave consistently in cost structure. This is genuinely new business intelligence.

• Learned distance metric — take pairs of historical projects, compute actual cost similarity, and train a lightweight model to predict which features best explain cost closeness. This is metric learning — the model learns "what makes two projects cost-similar" directly from outcomes.

• Feature interaction discovery — maybe material grade alone doesn't drive cost, but material × vessel type × PWHT together create distinct cost bands. Statistical interaction terms or decision tree models can surface these patterns.

The matching engine still stays explainable at query time — every result says which features matched and why. But the model behind the weights is now learned, not assumed.

What to tell the bosses: "The system now discovers hidden project families and cost patterns from your data. It knows that Aramco horizontal vessels in SA 516 with full RT cluster tightly and have consistent cost behavior — something no estimator explicitly tracks."

Resolved: OQ-04 is no longer an open question. The approach is clear: start with expert-seeded defaults (Phase 1), replace them with statistically derived weights as data grows (Phase 2), and evolve toward learned similarity models when the dataset is large enough (Phase 3). Each phase produces more accurate matching — and the transition is transparent and auditable. Initial expert defaults can optionally be sense-checked with GHI staff, but they are starting points to be overridden by data, not permanent truths.

Briefing as a First-Class Data Object

The briefing is not scattered results — it is a well-defined entity in the intelligence database, tied to an RFQ ID. It has a status (pending, partial, complete, failed), generation timestamps, confidence levels per section, and a version number (briefings can be re-generated as more data arrives).

This makes it queryable by any consumer: the UI can display it as a panel, the chatbot can navigate it conversationally, dashboards can aggregate briefing quality metrics, and workflows can trigger actions based on specific briefing flags.

Design decision: The briefing is generated asynchronously after the rfq.created event. It may take seconds to minutes depending on document complexity and LLM processing. The UI shows a "briefing in progress" indicator and renders sections progressively as they complete — document understanding first (fastest), then historical matching, then cost analysis (which depends on the first two).
Section 05

Four Capability Pipelines

Inside rfq_intelligence_ms — not autonomous agents, but four specialized processing pipelines with explicit brain types. Technically simple in phase 1. Extensible later.

Naming shift: Business-wise, "agents" is still a clear explanation for stakeholders. Technically, phase 1 treats them as four deterministic capability pipelines inside one service — not four autonomous mini-agents talking to each other. This avoids over-engineered internal orchestration while keeping the external narrative strong.

P2
Historical Matching
Algorithmic

Takes structured metadata from P1 and searches the historical database for similar past projects. Uses weighted field matching — not vector embeddings of raw documents. This is a deliberate design choice: with ~100 historical projects and clearly structured metadata fields, weighted scoring is faster, cheaper, deterministic, and more explainable than embedding-based similarity.

Partial similarity is expected and valuable. In custom manufacturing, no two projects are identical. The system ranks by degree of match across multiple dimensions: vessel type, material grade, tonnage range, standards required, client, RT type, PWHT requirement.

Similarity model: The three-layer similarity framework (technical/product, commercial/execution, cost behavior) is defined in detail in Section 04. P2 applies this model using weighted field matching — every result includes an explanation of which features matched and why. Weights start as expert-seeded defaults (Phase 1), are replaced by statistically derived values as historical data grows (Phase 2), and evolve toward learned similarity models in Phase 3. See Section 04 for the full discovery approach.
Input
Structured JSON metadata from P1 (current RFQ characteristics).
Output
Top N similar historical RFQs with similarity scores, full details: scope, tonnage, cost-per-ton, margin, outcome, delivery timeline, key differences.
P3
Cost Range & Scenario Analysis
Hybrid

Takes similar projects from P2 and produces a three-scenario preliminary cost analysis. The arithmetic is always algorithmic — LLMs hallucinate numbers. An optional LLM layer adds contextual caveats by reasoning over differences between the current RFQ and historical matches.

Best Case (Optimistic)
Lower quartile (25th percentile) of similar projects. Favorable assumptions: materials at current low prices, full internal fabrication, no design revisions.
Expected Case (Most Likely)
Median of similar projects, adjusted for known current conditions. Standard compliance costs, typical lead times. Most statistically reliable.
Worst Case (Pessimistic)
Upper quartile (75th percentile) + risk multipliers: subcontractor involvement, mandated premium suppliers, additional standards, market volatility.

The spread between best and worst is itself an insight. Narrow spread = high confidence, well-understood project type. Wide spread = high risk, proceed with caution. The system always shows reference count for transparency.

Confidence indicator: When ref_count < 5, the output displays a prominent "Low Confidence — limited historical data" warning. This manages expectations and prevents overreliance on thin data. As the database grows, confidence naturally increases.
Inputs
Similar projects from P2. Current market conditions (if available). RFQ-specific factors (PWHT, U-Stamp, mandated vendors).
Output
3-scenario cost range (best/expected/worst) with cost-per-ton benchmarks, dominant cost drivers, confidence level, reference count, contextual caveats.
P4
Supplier Intelligence
Hybrid

Maintains and queries supplier data. Simple queries (average price, lead time history, reliability score) are pure database aggregation — no LLM needed. Complex reasoning ("given this RFQ's material requirements, which suppliers should we consider and what risks exist?") uses LLM over structured supplier data.

For the proactive briefing: if the MR package includes an RVL (folder 03), the pipeline immediately identifies mandated vendors and surfaces their historical performance. If key materials are identified by P1, the pipeline checks known supplier pricing and availability.

Inputs
Material requirements from P1. Mandated vendor lists (RVL). Supplier history database. Market signals.
Output
Supplier profiles, price trends, lead time history, reliability scores, risk flags, availability signals, recommendations.

Section 06

Workbook Intelligence

The 36-sheet estimation workbook is the single richest data source in the platform. Because the template is identical for every RFQ, parsing is a deterministic engineering problem — not an AI problem.

What Intelligence Extracts from the Workbook

General Sheet
RFQ identity: client, inquiry ref, subject, project name, revision. Item table: tag numbers, descriptions, quantities, dimensions (ID×L), weight, material grade, vessel type (H/V), RT (Full/Spot), PWHT (Yes/No).
Bid Summary (Bid S)
Complete cost structure: material, labour, design, consumables, NDT, PWHT, paint, U-Stamp, NB, transport, financial charges, overheads, contingency. Each line in SAR, USD, percentage, and cost-per-ton.
Top Sheet
Revenue breakdown (normal/escalation/negotiation), total revenue, monthly cash flow projections (9 months), gross margin percentage, delivery timeline.
Material Cost Summary
Per-item material cost: unit weight, total weight, material cost, cost per kg (SAR and USD). Feeds into both cost analysis and supplier intelligence.
Weight Sheet
Reference lookup tables: flange weights by type/rating/size, pipe weights, standard component weights. Used by estimation but also valuable as a structured data source for intelligence validation.
Schedule (Sch)
Gantt-style phase durations: mechanical design, material procurement, detail engineering, drawing approval, fabrication/testing/painting/delivery. Timeline in weeks.
Financial Charges
Bank guarantee structures, LC costs, performance bonds, advance payment terms, negative cash flow calculations. Reveals payment structure and financial risk.
Bid Approval (Bid Appr)
Cost breakdown per SAP-style cost codes (1810-Material, 1820-Labour, 1843-Rental, 1840-Subcontractor, etc.). Maps costs to accounting structure.

Anomaly Detection — The Second Intelligence Moment

The briefing is the first intelligence moment (at arrival). Workbook validation is the second (during/after estimation). When a workbook is uploaded, intelligence parses it deterministically and compares values against historical patterns — but with a critical posture: the system never says "the workbook is wrong." It says "this deserves review." Every deviation may be a justified engineering choice. Intelligence surfaces it; the estimator decides.

Three safe anomaly families, ordered by reliability:

Family 1 — Structural / Completeness

Missing important cost lines that are present in comparable projects. Missing required workbook sections. Impossible or inconsistent totals. Broken percentage distributions. Mismatch between expected sheet content and actual uploaded content. These are the safest checks — they rely on workbook structure, not estimator judgment.

Family 2 — Benchmark / Outlier

Cost-per-ton far outside historical range for similar projects. Cost-line percentage share far outside comparable benchmarks (e.g., NDT at 8% when historically 1–2%). Margin much lower or higher than comparable client/project patterns. Schedule duration far outside similar project bands. These require sufficient historical data to define meaningful ranges.

Family 3 — Briefing vs. Actual

The preliminary cost envelope predicted 80K–100K SAR/ton; the actual workbook produced 120K. Intake identified PWHT or U-Stamp requirements; the workbook seems to miss their cost impact. These checks bridge the two intelligence moments — they only work when both the ZIP extraction and the workbook extraction are available.

What is NOT safe yet: Trying to infer every hidden estimator logic. Validating every formula decision. Assuming the workbook always follows stable patterns. Treating every deviation as an error rather than a justified engineering choice. The workbook is expertise-driven — intelligence adds a review layer around it, not a judgment layer over it.
Transparency requirement: Every anomaly flag must expose three things: (1) the comparable reference set used — which historical projects and how many; (2) the confidence level — how tight or wide the benchmark range is; (3) the reason for the flag — a plain-language explanation of what was compared and why it stood out. Without all three, the flag is not trustworthy and should not be surfaced to the user.

Anomaly detection improves with data volume. With 20 historical projects, benchmark ranges are wide and flags will be conservative. With 100+, they become tighter and more meaningful. This is expected and honest — the system should communicate its confidence level alongside every flag.

This directly solves PP-06: "The entire financial model for multi-million SAR projects lives in a single Excel file with 36 interconnected sheets. No version control, no audit trail, no concurrent editing. A broken formula in one sheet silently cascades across the entire estimation." Intelligence doesn't fix the Excel — it adds a validation layer that catches anomalies the Excel alone cannot surface.

The Two Extraction Templates Are Designed to Meet

The ZIP/MR package extraction (at arrival) and the workbook extraction (during estimation) are not independent data streams. They are designed with overlapping fields so that the system can compare what the RFQ asked for against how GHI priced it.

Shared comparable fields include: vessel/project type, material grade, weight/tonnage, applicable standards and process flags (RT, PWHT, U-Stamp), and cost-per-ton benchmarks. The ZIP extraction produces the briefing's preliminary cost envelope. The workbook extraction produces the actual estimate. The gap between them — "the briefing predicted X, the actual workbook produced Y" — is itself one of the most powerful intelligence outputs, because neither extraction template could produce it alone.

Simple rule: The ZIP tells us what the RFQ is asking for. The workbook tells us how GHI is planning to price and deliver it. Intelligence compares the two.

Opens new RFQ → Intelligence Briefing is already there.

Similar past projects with outcomes. Preliminary cost envelope. Client win/loss history. Compliance flags with cost implications. Instead of a 10–20 min undocumented gut check, they have data context. Their go/no-go decision gets captured structurally, feeding future predictions.

Section 08

rfq_chatbot_ms — The Thin Conversational Layer

Intentionally limited in scope. It navigates, explains, and extends intelligence — it never produces it.

What chatbot owns

Conversation session management and history. User intent detection and classification. RFQ context resolution ("which RFQ are we talking about?"). Deciding which backend service or pipeline to call. Response wording, formatting, and conversational UX. Citations, provenance, and explanation style. Guardrails and fallback behavior.

What chatbot does NOT own

RFQ parsing logic. Historical similarity logic. Cost computation or estimation logic. Supplier analytics logic. KPI calculation logic. Event subscriptions for proactive intelligence. The historical or analytical database. Any intelligence capability that another consumer also needs.

Chatbot's Real Value

The chatbot is not starting from zero. When someone asks "what do you know about this RFQ?" the chatbot surfaces the pre-computed briefing in conversational form. When someone asks "why is this flagged as high risk?" the chatbot explains the reasoning from the supplier and historical matching pipelines. When someone asks "what if we used 316L stainless instead of carbon steel?" the chatbot triggers a new targeted query to the cost pipeline — this is reactive, on-demand intelligence.

The chatbot's value is in navigation, explanation, and extension — making intelligence accessible to people who don't want to read structured reports, letting them drill down, ask follow-ups, and explore scenarios conversationally.

BACAB reuse angle: The conversation shell (session management, intent routing, response formatting, history, guardrails) can be reused from BACAB's existing chatbot codebase. What is NOT reused is the intelligence ownership model — intelligence moves out of chatbot tools into rfq_intelligence_ms. This is exactly where BACAB reuse becomes safe: reuse the conversation UX, not the intelligence logic.
Section 09

Cold Start & Historical Bootstrapping

The intelligence engine starts empty. It grows in two complementary ways.

Batch Seeding — Kickstart

Feed historical RFQs through P1

GHI provides past RFQ packages: MR folders + completed estimation workbooks + outcomes (won/lost, final price, actual costs). Even 20–50 historical projects create a meaningful foundation. The workbook is the richest source — each one gives you vessel specs, complete cost breakdown, margins, timelines, and payment structures. The MR folder gives compliance context and supplier constraints.

The estimation workbook format is identical across all historical RFQs, so the deterministic parser works on historical data exactly as it works on new data. No special migration logic needed.

Organic Growth — Continuous

Every new RFQ enriches the database

Each RFQ that passes through the system adds: parsed metadata, estimation data (when workbook is uploaded), outcome data (when result is recorded). The platform gets smarter with every project. Similarity matches become more precise, cost ranges become tighter, confidence levels increase, supplier data becomes richer.

This is the learning loop. No retraining, no data science overhead. The historical database grows naturally through normal platform usage.

Section 10

What Intelligence Does Not Own

Clear negative boundaries prevent rfq_intelligence_ms from becoming a dumping ground.

rfq_intelligence_ms should answer only questions of the form: What can we extract from RFQ documents? What past projects are similar? What preliminary cost range can we infer? What supplier patterns or risks exist? What historical benchmarks or anomaly thresholds do we know? What aggregate performance metrics can we compute?

RFQ lifecycle management (workflows, stages, transitions)
Communication drafting, reminders, or email templates
Conversation sessions, chat history, or user intent detection
User authentication, roles, or access control
Sending notifications or triggering external actions
File storage (documents live in Azure Blob — intelligence reads them)
Workflow execution or stage advancement decisions
UI rendering or response formatting for specific consumers

If a consumer (chatbot, dashboard, workflow) wants to act on intelligence — send a notification, block a stage, alert a manager — that action happens in the consumer's domain. Intelligence produces insight. Consumers decide what to do with it.

Section 11

Database Ownership

The strongest architectural argument for the split.

rfq_manager_ms — Operational DB

Owns live RFQ state: current status, stage progress, active blockers, pending subtasks, attached files, notes, deadlines. Optimized for transactional writes and lifecycle queries. PostgreSQL. Schema changes driven by workflow needs.

rfq_intelligence_ms — Historical & Analytical DB

Owns structured historical records: parsed RFQ metadata, cost breakdowns, outcome data, similarity features, supplier history, aggregate KPIs. Optimized for analytical reads, similarity search, and statistical computation. Schema evolves independently based on intelligence needs.

Data flow: Intelligence receives data via events (rfq.created, workbook.uploaded, outcome.recorded) and optional REST reads from rfq_manager_ms. It never writes to the operational database. This separation ensures the intelligence schema can evolve — adding new parsed fields, new similarity dimensions, new KPI structures — without impacting the core RFQ lifecycle.
Section 12

Phased Priorities & Feasibility

Not everything is equally ready on day one. This section defines what to build first, what depends on historical data, and what requires maturity before it becomes reliable.

The intelligence engine starts empty and grows with data. Capabilities should be released in phases that match the available data and the confidence the system can offer. Workbook-related intelligence is medium-to-high complexity and should be positioned as supportive, not authoritative — that wording protects the project from overpromising.

Phase 1 — Cold-Start Friendly

Safest, highest-value, no historical data dependency

Intelligence: MR package intake parsing (deterministic folder tree + LLM for unstructured docs). Standards and compliance auto-detection from folder 06 filenames. Intelligence briefing generation (document understanding sections). Historical database setup and schema. Workbook deterministic parser (the fastest way to populate the historical DB from GHI's past workbooks — this is cold-start infrastructure). Expert-seeded initial similarity weights (sensible defaults, to be replaced by data later).

Chatbot: Conversational explainer of the briefing. Basic RFQ context resolution. Retrieval of parsed metadata.

Dashboard: Structural foundations. Basic RFQ counts and status distributions from rfq_manager_ms data.

Demo-friendly early wins: MR folder tree parsing, standards auto-detection from filenames, intelligence briefing generation, workbook deterministic parsing. These are tangible, visual, and can be demonstrated to BACAB and GHI stakeholders without any historical data dependency. They show the platform "reading" real RFQ documents and producing structured outputs immediately.
Phase 2 — Requires Historical Base

Needs 50+ parsed historical workbooks + some outcomes

Intelligence: Structured similarity matching (Layer 1 technical features, using expert-seeded weights initially). Preliminary cost envelopes (3-scenario with confidence warnings). Client history and win/loss context. Supplier signals and mandated vendor intelligence. Basic post-upload structural/completeness checks on workbooks (Family 1 anomalies — safest).

Similarity weight calibration: With 50+ parsed workbooks, run correlation analysis and regression-based feature importance on the historical dataset. Discover which features (vessel type, material, tonnage, RT, PWHT…) actually drive cost-per-ton. Replace expert-seeded defaults with data-derived weights. This is new knowledge GHI has never had.

Chatbot: "Find similar projects" queries. "What do we know about this client?" queries. Cost range exploration.

Dashboard: Client-level win rate views. Pipeline funnel analytics. Basic margin tracking.

Phase 3 — Requires Maturity

Needs 100+ historical data points + outcome feedback loops

Intelligence: Benchmark/outlier anomaly detection (Family 2 — requires confident ranges). Briefing-vs-actual deviation analysis (Family 3 — requires both extractions). Bid strategy patterns and win probability modeling. Estimation accuracy tracking over time. Full three-layer similarity (including cost behavior layer). Portfolio-level aggregate analytics.

Advanced similarity: Unsupervised clustering to discover natural project archetypes. Learned distance metrics to find which feature combinations best predict cost similarity. Feature interaction discovery to surface hidden patterns (e.g., material × vessel type × PWHT creates distinct cost bands). The matching engine stays explainable — but the model behind it is now learned from data.

Chatbot: "What-if" scenario exploration. Margin impact analysis. Cross-RFQ pattern questions.

Dashboard: Executive-grade KPI dashboards. Department bottleneck analysis. Client profitability segmentation. Capacity utilization trends.

Why workbook parsing is Phase 1 even though workbook anomaly detection is Phase 2/3: Parsing the workbook is deterministic — the template is fixed, cell positions are known, and the parser can be written once and run reliably on every historical workbook GHI provides. This is the single fastest way to populate the historical database during cold start. Using that data for anomaly detection and benchmarking requires enough historical points to define meaningful ranges — that comes later.

Section 13

Academic & PFE Framing

How this design translates into thesis-defensible architectural vocabulary.

Event-Driven Architecture

rfq_manager_ms publishes domain events. rfq_intelligence_ms subscribes and reacts. Loose coupling, independent deployment, asynchronous processing. Standard EDA pattern.

CQRS-Adjacent Pattern

Manager handles commands (create, update, advance). Intelligence builds a read-optimized analytical projection of the same data, enriched with derived insights. Different schemas for different query patterns.

Bounded Contexts (DDD)

Operational lifecycle and historical intelligence are different bounded contexts with different schemas, query patterns, ownership, and evolution trajectories. Classic Domain-Driven Design separation.

Proactive vs. Reactive Intelligence

The system demonstrates both paradigms: proactive (event-driven briefing generation) and reactive (on-demand query answering). Combined with aggregate analytics, this shows a mature intelligence architecture.

Human-AI Collaboration

Intelligence assists, never replaces. The estimator keeps full control. The system adds a validation layer, historical context, and anomaly detection — augmenting human expertise rather than attempting to automate it. Directly aligned with the audit conclusion that BOQ automation is infeasible.

Continuous Learning Loop

Every RFQ outcome enriches future intelligence. No retraining required — the historical database grows organically. The platform gets smarter by existing. This is a defensible alternative to classical ML in low-data domains.
