Understanding BACAB's Current System

How Their Chatbot Architecture Works

A simple breakdown of the existing chatbot_ms + setup_ms pattern used in the real estate project, explained step by step.

01
The Four Pieces
The system has 4 main components, each running as its own container on Azure
⚙️
setup_ms

The Chatbot Factory

This is where an admin creates chatbot instances. Each chatbot gets: an ID, a system prompt, and a list of tools it can use. Think of it as a "template creator" — it defines what a chatbot knows and can do, then saves it all to the database.

🤖
chatbot_ms (api)

The Conversation Engine

This is the main service. When a user sends a message, this service loads the chatbot's config from the database (prompt + tools + history), bundles everything together, and sends it to Azure OpenAI. It then returns the response to the user. Endpoints: /ask, /history, etc.

📚
RAG + VDB

The Knowledge Layer

Documents are stored in Azure Blob Storage, chunked, embedded, and stored in a Vector Database. When the chatbot needs context (e.g., property details, documents), the RAG pipeline retrieves relevant chunks and feeds them into the conversation.

🗄️
Azure SQL Server

The Memory

Stores everything persistent: chatbot IDs, their prompts, their parameters, conversation histories, and tool configurations. Both setup_ms and chatbot_ms read/write here.

💡 Simple Analogy: Think of it Like a Restaurant

setup_ms = The manager who creates the menu (defines what each chatbot can do).
Database = The recipe book (stores prompts, tools, conversation history).
chatbot_ms = The waiter who takes orders, goes to the kitchen, and brings back food.
Azure OpenAI = The chef who actually cooks (the LLM that reasons and responds).
RAG/VDB = The pantry (stored knowledge the chef pulls ingredients from).

The waiter (chatbot_ms) doesn't cook — he just carries things back and forth. But the chef (LLM) decides everything: what ingredients to use, how to combine them, what tools to call. The waiter just facilitates.

02
What's Stored in the Database
Each chatbot instance is a row with its own configuration
Field Example (Real Estate Bot) What It Does
chatbot_id "bot_realestate_01" Unique identifier for this chatbot instance
prompt "You are a real estate assistant. Help users find properties based on their criteria. You have access to the property database..." The full system prompt — personality, instructions, context
params { temperature: 0.7, model: "gpt-4" } LLM settings and any extra configuration
tools [search_property, get_price, schedule_visit, ...] List of tools/functions the LLM can call
conversations [ {id: "conv_123", messages: [...]} ] Full history of all conversations under this chatbot

💡 Why Multiple Chatbots?

In the real estate project, they might have: one chatbot for property search (prompt about finding apartments, tools for search/filter), another for admin tasks (prompt about managing listings, tools for CRUD operations), another for client support (different prompt, different tools). Same engine, different configurations. The admin creates each one through setup_ms.

    chatbot_ms

  • 7
    Azure OpenAI

  • 8
    chatbot_ms

05
The Key Insight
Now that you understand the system — here's what matters

Who's Actually Making the Decisions?

In this architecture, chatbot_ms is essentially a delivery service — it carries messages back and forth between the user and the LLM. The real question is: who decides what to do with the user's request?

The answer: the LLM decides everything. It reads the prompt, sees the tools, and autonomously chooses which tools to call, in what order, and how to interpret the results. There is no code in chatbot_ms that says "if the user asks about prices, do X then Y then Z." The LLM figures that out on its own every time.

This is the LLM-as-orchestrator pattern. It works beautifully when:
— Queries are open-ended and conversational
— There's no single "right answer"
— Mistakes are low-cost (wrong apartment suggestion → user just scrolls past)

The question for GHI is: is this the right pattern when a wrong cost estimate means real financial loss?
