Key interaction patterns: Manager → Intelligence is primarily event-driven (lifecycle events trigger proactive intelligence). Intelligence → consumers is request-response (structured JSON APIs). End-to-End RFQ Lifecycle Flow

The "movie" of the platform — what happens from the moment an RFQ arrives to the moment its outcome is recorded. Each step shows who is responsible and what is produced.

RFQ Journey — From Arrival to Outcome
External
1. RFQ Arrives
Client sends email with ZIP file containing MR package (numbered folder tree: 00-Approval through 15-Notes to Vendor, plus BOM, RVL, specs, standards, drawings). May also arrive via SAP Ariba portal.
ZIP / MR packageEmail / SAP Ariba
Manager
2. RFQ Registered
rfq_manager_ms creates the RFQ record, assigns a workflow, clones stage instances, and stores documents in Azure Blob Storage. Status moves to "In preparation."
rfq.created event publishedFiles → Azure Blob
Intelligence
3. Proactive Intelligence — Briefing Generated
rfq_intelligence_ms receives the event and activates automatically. Two-layer parsing: deterministic extraction (folder tree, BOM Excel, standard filenames) + LLM for unstructured docs (specs, scope, QA/QC). Produces the Intelligence Briefing — a persistent dossier with: document understanding, similar past projects (partial similarity — Layers 1+2), preliminary cost envelope, client history, compliance flags, supplier signals.

4. Briefing Available on RFQ Overview
The UI displays the briefing as a panel on the RFQ overview page. Sections render progressively as they complete. Manager opens the RFQ and the system has already done homework.
Briefing panelManager reviews
Human
5. Feasibility Decision
Department manager reviews the briefing and makes go/no-go decision with data context instead of undocumented gut check. Decision captured structurally — reasoning, risk factors — feeding future analytical patterns.
Decision → Historical DBPP-07 solved
Human
6. Estimation — Workbook In Progress
Estimator works on the 36-sheet workbook (their domain — the platform does not guide or prescribe). Historical reference context is available on demand through the briefing, the RFQ overview, or the chatbot. Pull-based: the estimator consults when they want to.
Expertise-driven workBenchmarks on demand
Chatbot
Available throughout — Thin Orchestrator
At any point from step 4 onward, a user can open the chatbot. It does not own any lifecycle step. Its role is to navigate, explain, and extend intelligence: "show me the briefing for this RFQ" → calls intelligence. "What stage is this RFQ at?" → calls manager. "Find similar projects with PWHT" → calls intelligence. "What if we used 316L stainless?" → calls intelligence cost pipeline. The chatbot orchestrates calls to other services and presents the answers conversationally.
Calls rfq_intelligence_msCalls rfq_manager_msOwns only conversation UX

7. Workbook Uploaded
rfq_manager_ms receives the estimation workbook file upload (type: "Estimation Workbook"). File stored in Azure Blob.
workbook.uploaded event publishedWorkbook → Azure Blob

8. Workbook Validation — "This Deserves Review"
rfq_intelligence_ms parses the workbook deterministically (same template, fixed cell positions). Compares values against historical patterns. Three safe anomaly families: (1) structural/completeness gaps, (2) benchmark outliers vs. similar projects, (3) briefing-vs-actual deviations. Posture: review, not judgment.

9. Bid Strategy Support
Before bid submission, intelligence provides margin-vs-win-probability analysis: "at 8% margin, similar projects had 65% win rate with this client." 3-scenario cost range with confidence levels. These are advisory historical signals, not pricing recommendations. The bid decision remains entirely with GHI leadership — intelligence provides context, not instruction.

RFQ reaches terminal state: won, lost, or declined. rfq_manager_ms records the outcome.

11. Feedback Loop — The System Learns
The outcome enriches the historical database. The system now knows: for this vessel type, with this client, at this margin, the result was X. Future similarity matching becomes more precise, cost ranges tighter, confidence higher. No retraining needed — the database grows organically.

Chatbot's role in the flow: The chatbot is shown as a dashed side-lane because it does not own any lifecycle step — it is available throughout. Its role is thin orchestration: receive a user question, determine which backend service has the answer (intelligence for analytical data, manager for operational state), call the right API, and present the response conversationally. It produces no intelligence of its own.

Diagram 04

Data Ownership

Each core service owns its own database. No shared DB. Intelligence receives data via events and optional REST reads — it never writes to the operational database.

Database Ownership — Three Bounded Contexts

Operational Database

Owned by rfq_manager_ms
PostgreSQL · Transactional writes
  • Live RFQ records & status
  • Workflow templates & stage instances
  • Stage progress & blocker state
  • Subtasks & assignments
  • Notes (append-only)
  • File metadata (refs to Blob)
  • Deadlines & reminders
  • History / audit log

Historical & Analytical Database

Owned by rfq_intelligence_ms
Schema evolves independently
  • Parsed RFQ metadata (structured JSON)
  • Workbook extracted data
  • Cost breakdowns & benchmarks
  • Similarity feature vectors
  • Intelligence Briefings (persistent artifacts)
  • Validation & anomaly reports
  • Outcome records & feedback data
  • Supplier history & price trends
  • Aggregate KPIs & portfolio analytics
  • Similarity weight calibration data

Session Store

Owned by rfq_chatbot_ms
Conversation-optimized
  • Conversation sessions
  • Message history
  • User intent context
  • RFQ context resolution state
  • Guardrail / fallback config
rfq_manager_ms —— events ——→ rfq_intelligence_ms ←— API calls —— rfq_chatbot_ms
Shared Infrastructure
Azure Blob Storage
—
Document & file content (MR packages, workbooks, drawings, specs). Not a database — no business logic, no queries. Manager writes file references. Intelligence reads file content for parsing. Shared by all services that need document access.
Data flow principle: Manager publishes events (rfq.created, workbook.uploaded, outcome.recorded). Intelligence subscribes, processes, and stores results in its own DB. Chatbot calls Intelligence and Manager APIs to serve user queries — it stores only conversation state. Azure Blob Storage is shared infrastructure for file content but is not a database.
